# How GRUB picks what to boot

Short version: it is a number, it counts entries in file order, and the file is
usually on a FAT32 partition that nothing mounts for you.

## Where the config lives

GRUB reads the config that sits next to its own binary on the EFI system
partition. Common layouts:

```text
/boot/efi/EFI/grub/grub.cfg          hand-written, Arch and friends
/boot/efi/EFI/ubuntu/grub.cfg        generated by grub-mkconfig on Ubuntu
/boot/efi/EFI/GRUB/grub.cfg          same as the first, different case
/boot/efi/EFI/fedora/grub.cfg        generated
/boot/grub/grub.cfg                  BIOS machines only
```

FAT32 is case-insensitive, so `EFI/grub` and `EFI/GRUB` are the same directory.
`bootpick` does not care about case.

On most desktops the ESP is mounted at `/boot/efi`. On Arch with a separate
`/boot` it often is not mounted at all, which is why changing the boot default
needs root and a mount before it can even see the file.

## `GRUB_DEFAULT` is not the same thing

`/etc/default/grub` contains `GRUB_DEFAULT=0`, and `grub-mkconfig` turns that
into `set default=0` in the generated file. Two consequences:

- If your config is **generated**, edit `/etc/default/grub` and re-run
  `grub-mkconfig -o /boot/grub/grub.cfg` (or the path your distro uses).
  Editing the generated file works until the next kernel update.
- If your config is **hand-written**, `/etc/default/grub` is not read by
  anything and `set default=` in the file is the whole truth.

`bootpick` only ever edits the file itself. That is the right thing for a
hand-written config and the temporary thing for a generated one. The README says
so too, because a tool that silently loses a setting at the next update is worse
than no tool.

## The numbering, exactly

GRUB walks the file top to bottom. At the top level, every `menuentry` and every
`submenu` gets the next number, in the order they appear. Inside a submenu, the
children are addressed as `<parent>><child>`.

```text
menuentry "Ubuntu"                    → 0
menuentry "Omarchy"                   → 1
submenu "Advanced options"            → 2
    menuentry "rescue shell"          → 2>0
    menuentry "older kernel"          → 2>1
```

So:

```
set default=0     Ubuntu
set default=1     Omarchy
set default=2     opens the submenu, does not boot anything
set default=2>0   rescue shell directly
```

Two things bite people here. A `submenu` consumes a top-level number even though
it is not bootable, so inserting one shifts everything after it. And
`GRUB_DEFAULT` in `/etc/default/grub` also accepts `saved`, which reads a
persisted entry from `grubenv` instead of counting, which is a different
mechanism entirely.

## Timeout

```
set timeout=5
set timeout_style=menu
```

`timeout=0` boots the default immediately with no menu (holding a key usually
still gets you one, depending on the build). `timeout=-1` waits forever.
`timeout_style=menu` forces the menu to be drawn instead of the bare countdown
line.

## The one-shot trick

`grub-reboot` sets an entry for exactly one boot and then reverts:

```sh
sudo grub-reboot 'Omarchy'
sudo reboot
```

This is the safest way to test a new kernel or a new entry, because a failure
reboots back into the entry that works without anyone touching a keyboard. It
writes to `grubenv`, which lives on the same ESP.

## Validating before you reboot

GRUB ships a config checker:

```sh
sudo grub-script-check /boot/efi/EFI/grub/grub.cfg
```

Silence means it parses. `bootpick` runs this automatically on every write and
rolls the file back if it complains. That single step is the difference between a
boot config and a bricked menu.

## When the config is regenerated

`grub-mkconfig` runs on kernel updates on most distros and rebuilds the menu from
scratch, including os-prober's guesses about the other operating system. Prober
output order is not stable between runs, so `GRUB_DEFAULT=0` can mean a different
OS after an unrelated update. If you need a stable default across regenerations:

- set `GRUB_DEFAULT` to the **exact menu text**, quoted, which survives
  reordering, or
- set `GRUB_DEFAULT=saved` and use `grub-set-default` / `grub-reboot`, or
- keep a hand-written config and stop running `grub-mkconfig` over it.

`bootpick` uses numbers because that is what `set default=` stores, but `set`
accepts a name and resolves it for you, so you never have to count by hand.
